Guide -- what is this, and what should I expect to see?

What is this

This is an automatic watcher: it continuously compares "what should be happening" in the industrial lab (the PLC, sensors, security software) against "what is actually happening right now", and flags it when something doesn't match. It is not just a screen that shows data -- it is a program that checks the system on its own, every 30 minutes, with nobody needing to come look.

Objectives

1. Know at any moment whether the scenario (the 5 virtual machines simulating the factory) is still exactly as deployed, without anyone checking by hand.
2. Automatically detect 3 real kinds of problem: a security tool that disappears, a service that stops, or the PLC doing something its own program would never do.
3. Leave a verifiable record of every problem detected -- date, what happened, why it counts as a problem -- usable as real evidence for a forensic investigation.
4. Do all of this while spending as little of the host's resources as possible.

What results to expect

Healthy case (normal, almost always): Missing tools: none · Clock: synchronized · PLC: diverged=false everywhere · Events list: "no divergence events recorded".

Real-problem case (what this is built to catch): A tool shows up under Missing · A service shows as not active · The PLC shows diverged=true · A new row appears under "Recent Divergence Events", with a date, a problem type, and an explanation.

Important: everything coming back "healthy" does not mean the system is doing nothing. It means it genuinely checked and found no problem -- that is an active confirmation, not an empty result.

FAQ

If everything comes back healthy, does that mean the digital twin isn't doing anything useful?
No. It means that, right now, there is no problem -- and that is already real information, actively verified every 30 minutes.

Do I need to launch an attack campaign for this to work?
Not for the basics. It already watches whatever scenario is currently deployed. A campaign is only needed for the specific reproducibility check (button 2).

Can this slow down the rest of the platform?
The automatic cycle is designed to be cheap: about 20 real seconds of work every 30 minutes.

Why are the clock and the PLC only checked every 2 hours instead of every 30 minutes?
Because they are the most expensive checks (they need a real network connection to each machine). They run less often to avoid wasting resources, but they still run on their own, with nobody needing to ask.

1 · Check a Node

Pulls fresh tool inventory and a live clock reading (plus PLC control-law state for role=plc). The clock reading is a real SSH round-trip -- a few seconds, never automatic or continuous.

2 · Check Campaign Reproducibility

Reuses the Level C comparison_report already computed between repetitions -- never recomputes CPR/WCPR itself.

3 · Check Scenario Snapshot

Reuses the 2 most recently captured whole-scenario snapshots already built by scenario_snapshot -- never triggers a new capture. Fires an event only on a real readiness regression (overall_reproduction_ready=False), not on a mere hash change (which happens between almost every pair of snapshots, since it includes platform-wide monotonic counters).

4 · Config Integrity (Suricata/Wazuh)

Hashes the same Suricata rule files and Wazuh config/rule files the tooling probe already reads over SSH, and compares them against a baseline you capture explicitly. Uses the node selected above in "1 · Check a Node". The PLC's own program file is not covered -- it has no confirmed remote path in this codebase yet.

5 · Network Exposure (ports/sessions)

Live ss -tulwn (listening TCP/UDP ports) and who (logged-in sessions), reusing the same health-probe SSH session node_health already opens. Grounded in NIST SP 800-86 §5.1.2 "Volatile Data" -- Network Connections and Login Sessions are two of its named volatile-evidence categories. Uses the node selected above in "1 · Check a Node". A new listening port vs. the baseline is flagged as a divergence (classic backdoor/persistence indicator); login sessions are shown as real, honest context, never auto-flagged (a real admin SSHing in to administer the lab is routine here, not an anomaly).
